03
Secret · 密钥的一生

明文只活在两个进程的内存里

手机输入 → SSH stdin（探测用）→ 宿主内存 → secrets/<id>（0600）→ turn 启动时读回 → HTTP 头。除此之外任何地方出现的都只是掩码。

手机输入框用户键入，内存中
→
SSH stdin只给 /models 探测用
→
provider/createJSON 正文，一次
→
secrets/<id>0600 明文，唯一持久副本
→
AuthorizationBearer，发给模型

密钥不会出现的地方

  • providers/providers.json — 只有 hasApiKey 与掩码，索引可随便看
  • RACP 响应、events.jsonl、错误体 — view() 直接把 apiKey 置空
  • idempotency.json — 含令牌的方法被排除，重放不会带出密钥
  • 项目目录下的 .pi-host-auth.json — 实测是空对象 {}，密钥只在内存里传给 SDK
04
Two paths · 两条出网路径

同一台服务器，两套 HTTP 客户端

这是最容易看错的一段：模型列表不是宿主查的，对话也不是手机发的。两条路径之间没有共享代码，只共享 baseUrl 与 key。

路径 A · 列模型

GET {baseUrl}/models · 走 SSH exec

手机→ SSH exec→ 服务器 python3→ 模型服务

脚本以 base64 内嵌在命令里，参数走 stdin。只接受同源重定向，读满 2 MiB 就停。结果以 PI_MODELS_RESULT 前缀回显在 stdout，手机解析成模型清单。

路径 B · 发对话

POST {baseUrl}/chat/completions · 走宿主 SDK

手机→ RACP turn/start→ 宿主进程→ 模型服务

宿主把密钥读回内存，注册成 openai-completions provider，SDK 用 baseURL = model.baseUrl 建客户端，stream: true 发出。手机只收到已经标准化的事件，看不到这个 HTTP。

06
Failure map · 失败点

这条链上会断在哪

每一跳都有确定的失败形态。知道断点，比知道链路更有用。

断点触发条件表现
① 探测baseUrl 打不通 / 超时 / 跨源重定向手机侧 ModelListError，模型清单为空，但 provider 仍可手填模型
④ provider/createbaseUrl 是 http，或解析到私网、loopback、元数据地址INVALID_ARGUMENT：endpoint must use https / private endpoint is forbidden
④ provider/createauthKind=api_key 却没给密钥；authKind=none 却给了INVALID_ARGUMENT
④ provider/createvendorKey 重复CONFLICT：provider vendorKey already exists
⑧ turn/start会话没绑 provider 或 modelPROVIDER_NOT_CONFIGURED：provider is required / model is required
⑨ 读密钥secrets 文件被手工删掉PROVIDER_SECRET_MISSING
⑩ 发请求模型名不在服务端、key 过期、baseUrl 少写 /v1驱动捕获后发 turn.failed，error 里是 provider 返回的原文
